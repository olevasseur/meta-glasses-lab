# Conversation latency — 2026-10-08

**Token startup improved; a steady-turn speech latency improvement is not established.**
Six matched cold-transport sessions versus six final keepalive sessions measured a
median `/token` reduction from **239 to 154 ms** (86 ms / 36%). Total token +
WebSocket + setup fell from **631 to 542 ms**. Auto's configured 2000 ms patience
is unchanged. The final Auto audio samples were **2962 and 7578 ms**, demonstrating
provider/transport variability rather than an inference speed win.

## Method and budget

Used `scripts/voice_eval/latency.py`, based on the existing real-PCM headless client.
The production authenticated `/token` handler and real Google auth_tokens.create
were exercised through FastAPI TestClient. Live used the verified constrained
v1beta endpoint, ephemeral Authorization header and minimal model/resumption setup.
The same cached Kore “Add a note to my Inbox: buy oat milk tomorrow” PCM was sent
at realtime speed with 300 ms pre-roll. The fixture duration and SHA256 are in
[raw measurements](latency-2026-10-08.json).

Auto sends silence to let server VAD finish. PTT sends activityEnd at the fixture
endpoint. Over uses the existing harness's oracle endpoint plus 1.2 seconds of
silence, **not actual keyword recognition**. The utterance is identical in all
three modes so the manual probes exercise activityEnd, not recognition of “over.”
Docs services are simulated; actual tool selection, argument generation and audio
come from Gemini. Backend memory is temporary. No real Google Docs writes, new
TTS generation, hardware calls or health probes were made.

Exactly **24 Live sessions**, one at a time, all closed:

| Run | Sessions | Purpose |
| --- | ---: | --- |
| `before` | 6 | Initial untouched-runtime pilot; 1 s settling was too short for one Over audio continuation |
| `before-cold` | 6 | Baseline with fresh token transport each request, 5 s settling |
| `after-reuse` | 6 | Reused SDK client with default 5 s HTTP keepalive; no useful token gain (median 242 ms) |
| `after-keepalive` | 6 | Final 120 s keepalive; 5 s settling |

The baseline explicitly closes the pooled transport before each token request to
reproduce the original cold connection/client creation. That close is outside its
HTTP timer; unlike the original, cleanup occurs before rather than after the
request, a small limitation of the emulation. The untouched pilot's token median
was 268 ms and its Auto audio median was 2971 ms. The pilot's missing-audio result
is preserved, excluded from the matched tables, and the probe now stops on an
audio-less result. There were **no 429, 1011 or 503 errors**, no automatic retries,
and no sessions left open. No further probes were run to seek favorable samples.

**68%** of the 2934 ms total. Subtracting 2000 ms gives an **estimate** of the
remaining delay, not isolated model compute. The fixture endpoint can include
trailing silence, and Google's boundary is not exposed here. Tool response timing
is already included in those totals and must not be added again.

## Implemented changes and expected effect

- Start/capture begins token + Live setup before awaiting audio route negotiation.
  For measured Live time `L` and hardware route time `R`, startup changes from
  approximately `R + L` to `max(R, L)`. The overlap saves up to `min(R, L)`; actual
  hardware savings are unverified. Paused or not-yet-ready audio stays gated.
- Reuse one backend SDK transport, with 120-second idle keepalive and at most two
  connections. Fresh token constraints and `uses=1` are retained. No stale token
  bank or screen-open speculative Live sessions are introduced. Mode/persona and
  memory are rebuilt on every token request. Shutdown closes the transport.
- Retain warm Live/audio routes between turns and existing concurrent tool jobs.
  Unit tests now explicitly verify one token across two turns, first-chunk delivery
  before turnComplete and two tools starting before either finishes.
- Request a smaller effective AudioTrack buffer and first-write playback; reserve
  at least 200 ms capacity. Active queued underruns grow it in 20 ms steps, bounded
  by capacity; idle underflows do not grow it. The application queue still caps at
  40 seconds and interruption flushes it. This does not eliminate network gaps or
  prove a 60 ms acoustic improvement.
- Optional slow-tool sound after 1.5 s, off by default. It neither speeds the
  provider nor indicates completion; cancellation/fast completion prevents a
  delayed tone. See [feature controls and limitations](../features/latency.md).
- Add safe stage timings and route/buffer diagnostics for hardware follow-up.
  Backend notes already had a five-minute Drive cache and persistent Google
  clients. Its transport lock is required for correctness and remains intact.

updated memory/mode constraints, key/timeout rotation, shutdown, playback growth,
idle gaps, warm-session audio gating, concurrent tools, delayed-cue cancellation,
cue speaker failure, settings persistence and waterfall arithmetic.

Hardware follow-up: capture `latency` diagnostics for Start and two Auto/Over
turns; verify audio route readiness, actual buffer size, underruns, first-chunk to
