## Focused backend fix

`Memory.recall` repeatedly appended adjacent chunks to the same string, copying
an increasingly large transcript while holding the memory lock. A synthetic
72,000-row fixture (the two-hour load volume) took **65.99 seconds** to recall one
saved bicycle fact. Joining each adjacent speaker/session group once reduced the
same query to **1.04 seconds**, with the same result. Profiling then identified
unthresholded RapidFuzz matching as a second issue: a join-only process peaked at
1,023 MiB. Passing the existing minimum qualifying score (`score_cutoff=65`) into
WRatio reduced the final query to **0.43 seconds and 354 MiB peak RSS**. All score
consumers already require at least 65; accepted rankings and the higher forgotten
content thresholds are preserved. These are individual synthetic benchmark runs,
not production latency guarantees.

The changes are limited to chunk joining and the fuzzy cutoff in `backend/memory.py`. New regressions
preserve speaker/session boundaries and the existing 2,000-character result cap.
This remains a linear in-memory search; it is not an unbounded-history solution.
The soak imported the original backend before this fix, so its Auto/resource
measurements are baseline evidence. The isolated before/after benchmark
and regression tests validate the fix; no second credentialed endurance run is
silently counted as having tested it.
